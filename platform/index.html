PlatformInfrastructure overview

The platform behind every engagement.

One governed system is designed to run both services, from request to report. This is how it fits together and where the boundaries sit.

Request a technical briefing

Seven layers, one direction of travel

A request moves down through the same seven layers every time. Nothing reaches a test environment without passing the authorization layer first.

  1. Engagement interface

    Requests arrive through a web console, the command line or chat. Nothing runs from here directly.

  2. Authorization and scope controlauthorized

    Every action is checked against a written authorization: scope, time-box and target allowlist. Out-of-scope requests are refused with a reason.

  3. Orchestration core

    A planner breaks the work into steps, picks the model lane and tool for each, and records every run in a ledger.

  4. Execution harnesses

    Isolated workers carry out the steps: they write probes, run commands and call tools, each with its own credentials.

  5. Assessment tooling

    Mobile static and runtime analysis, code and dependency scanning, web testing and passive reconnaissance.

  6. Isolated test environments

    Disposable, network-segmented environments: ephemeral containers, an emulated device farm, loopback labs and client-authorized staging.

  7. Evidence, analysis and reporting

    Raw artifacts are stored with hashes, findings are written from them, and reports are sanitized on export.

Lessons from each engagement return to the knowledge layer, so the next one starts from the last.

Model lanes

Work is routed by difficulty, so depth is paid for only where it is needed.

Frontier

Hard reasoning and judgment.

  • Decode an obfuscated record table
  • Plan a controlled comparison
  • Review a finding before it ships

Cost-efficient

Routine, well-defined steps.

  • Extract fields from launch logs
  • Assemble the report
  • Check a run against its runbook

Self-hosted

Work that should not leave our environment.

  • Process client artifacts that must stay with us

Built on an enterprise model platform

Model access is designed around a leading frontier-model provider's enterprise platform and console, used as infrastructure rather than as the product.

Workspaces per lane

Each model lane runs in its own workspace, so lanes never share keys, limits or logs.

Scoped keys

Keys are issued per workspace and per worker, and rotated. They never appear in reports or logs.

Spend limits

Every engagement has a cost ceiling, enforced at the workspace level.

Usage logs

Model calls are logged and tied back to the run ledger, so every step can be traced.

No training on our data

We choose providers whose commercial terms exclude our inputs and outputs from model training.

Provider-independent

The orchestration core addresses lanes, not vendors. A lane can change provider without touching the layers above it.

Controls at every layer

Identity and secret isolation

Per-lane and per-client credentials; no path from one client to another.

Data-boundary control

Client artifacts stay in their workspace; exports pass a redaction step.

Auditability

Every action is attributable to an actor and an authorization reference, and reproducible.

Safe defaults

Passive and read-only first; anything intrusive needs recorded authorization and is time-boxed.

What clients see, and what stays internal

Clients see

  • Intake and scope
  • Authorization records
  • Reports and evidence export

Stays internal

  • Orchestration and model lanes
  • Execution harnesses
  • Runbooks and the knowledge layer
